# نشر قواعد Firebase تلقائياً

## المشكلة التي يحلّها هذا الملف

قواعد `firestore.rules` و`storage.rules` هي حدّ الأمان الحقيقي في هذا
التطبيق: الواجهة تتصل بقاعدة البيانات مباشرة، فأي فحص داخل المتصفح قابل
للتجاوز. لكن **دمج القواعد في `main` لا ينشرها**. حدث هذا فعلاً: قواعد
مُصلَحة ومُختبَرة بقيت في المستودع بينما الإنتاج يعمل بنسختها القديمة.

الآن تتكفّل مهمة `deploy-firebase-rules` في
`.github/workflows/security.yml` بالنشر عند كل دمج في `main`، بعد نجاح
اختبارات القواعد الـ28 على المحاكي الرسمي. لا تُنشر قاعدة لم تُختبر، ولا
تبقى قاعدة مختبَرة غير منشورة.

يبقى إعداد واحد لمرة واحدة: سرّ الاعتماد.

## الخطوة الوحيدة المطلوبة منك

### 1) أنشئ حساب خدمة بأقلّ صلاحية

السرّ ليس قيمة جاهزة تنسخها من مكان ما في Firebase — أنت تُنشئها. وأمامك
طريقان، والفرق بينهما جوهري.

في [Google Cloud Console](https://console.cloud.google.com/iam-admin/serviceaccounts?project=gen-lang-client-0759922046)
للمشروع `gen-lang-client-0759922046` — وهي الطبقة نفسها التي تجلس تحت
Firebase، بالحساب نفسه:

1. **Create service account**
2. الاسم: `github-rules-deployer`
3. امنحه هذين الدورين فقط:
   - `Firebase Rules Admin` (`roles/firebaserules.admin`) — نشر القواعد
   - `Firebase Viewer` (`roles/firebase.viewer`) — قراءة بيانات المشروع

هذان الدوران يكفيان لنشر القواعد ولا يكفيان لقراءة بيانات المستخدمين ولا
لحذف شيء. لو أخفق النشر برسالة صلاحية، أضف
`Service Usage Consumer` (`roles/serviceusage.serviceUsageConsumer`).

> **تجنّب الطريق السريع.** زرّ **Generate new private key** في
> [Firebase ← Project settings ← Service accounts](https://console.firebase.google.com/project/gen-lang-client-0759922046/settings/serviceaccounts/adminsdk)
> أسرع، لكنه يعطي مفتاح حساب `firebase-adminsdk` الافتراضي: يقرأ ويكتب
> ويحذف كل بيانات Firestore وكل ملفات التخزين، **ويتجاوز القواعد نفسها**.
> مفتاح واحد مسرَّب هناك يساوي كل بيانات مستخدميك. يعمل للنشر، لكن الثمن
> لا يستحق الدقيقة الموفَّرة.

> ولماذا حساب خدمة بدل `firebase login:ci`؟ لأن رمز `login:ci` يمثّل حسابك
> كاملاً وبكل مشاريعك ولا ينتهي. حساب الخدمة هنا محصور بمشروع واحد وبفعل
> واحد، ويمكنك إبطاله وحده متى شئت.

### 2) نزّل مفتاح JSON

في حساب الخدمة الذي أنشأته: تبويب **Keys** ← **Add key** ←
**Create new key** ← **JSON** ← **Create**.

> **لا تنسخ ما تراه في جدول Keys.** ذلك العمود هو *معرّف* المفتاح
> (`private_key_id`) — أربعون محرفاً ست عشرياً — لا المفتاح نفسه. المفتاح
> يُنزَّل ملفاً ولا يُعرض على الشاشة أبداً. وقعنا في هذا فعلاً، ولذلك صار
> سير العمل يكشفه بالاسم.

يُنزَّل ملف بهذا الشكل:

```json
{
  "type": "service_account",
  "project_id": "gen-lang-client-0759922046",
  "private_key": "-----BEGIN PRIVATE KEY-----\n…",
  "client_email": "github-rules-deployer@…"
}
```

### 3) ألصقه في أسرار المستودع

مباشرةً عبر
[Settings ← Secrets and variables ← Actions ← New repository secret](https://github.com/hasaniraq66/-/settings/secrets/actions/new)

- الاسم: `FIREBASE_SERVICE_ACCOUNT`
- القيمة: محتوى ملف JSON كاملاً، من `{` إلى `}`

> **الخطأ الأشيع — وقعنا فيه فعلاً.** لا تفتح الملف في محرر يعيد تنسيق JSON.
> حقل `private_key` يحوي `\n` كحرفين، ومحرّرٌ يحوّلهما إلى أسطر حقيقية يجعل
> الملف JSON غير صالح. انسخه كما نزّلته: `cat` في الطرفية، أو فتحٌ بمحرر نصوص
> عادي، ثم نسخ الكل.
>
> يقبل سير العمل أيضاً القيمة مرمَّزة بـ base64، ويتجاوز مسافات البداية
> والنهاية وعلامة BOM. وإن أخفق التحقق فهو يسمّي السبب — نسخٌ جزئي أم أسطر
> محوَّلة — من دون طباعة أي جزء من المفتاح.

### 4) احذف الملف المُنزَّل من جهازك

انتهى دوره. نسخته الوحيدة الباقية داخل أسرار GitHub مشفّرة.

> **لا تلصق هذا المفتاح في محادثة — لا معي ولا مع غيري.** المحادثات تُخزَّن.
> السرّ يمرّ من متصفحك إلى إعدادات المستودع مباشرة، ولا يمرّ بمكان ثالث.

### 5) شغّل النشر أول مرة

من تبويب **Actions** ← سير العمل
**Security, quality, and deployment health** ← **Run workflow** على فرع
`main`. بعدها يعمل تلقائياً مع كل دمج.

## ما الذي يفعله سير العمل بالضبط

| الخطوة | السلوك |
| --- | --- |
| السر غائب | تحذير ظاهر في ملخّص التشغيل، ولا يُكسر الدمج |
| السر ليس JSON صالحاً | إخفاق فوري برسالة واضحة |
| المفتاح يخصّ مشروعاً آخر | **رفض النشر** بدل إرسال القواعد إلى المكان الخطأ |
| كل شيء سليم | نشر `firestore:rules` و`storage` معاً، وبصمة كل ملف في الملخّص |
| بعد النشر أو إخفاقه | محو المفتاح من قرص المشغّل دائماً |

المفتاح يُكتب خارج مساحة العمل (`$RUNNER_TEMP`) بصلاحية `umask 077`، فلا
يلتقطه أمرٌ يمشّط المستودع، ولا يظهر في السجلّات: GitHub تحجب قيمة السرّ.

## قاعدة البيانات المستهدفة

المشروع لا يستخدم قاعدة `(default)` بل قاعدة مسمّاة:
`ai-studio-3f3fe98c-ba52-4ec9-8fd3-456c5b910cc1`.

لذلك يعرّف `firebase.json` مفتاح `firestore` **كمصفوفة** بحقل `database`.
الشكل المفرد ينشر إلى `(default)` وينجح بصمت بينما تبقى قاعدة التطبيق بلا
حماية — وهذا أخطر من إخفاق واضح. يحرس هذا التطابقَ ملفُ
`server/firebaseRulesDeployment.test.ts`، ويقارنه بـ
`client/firebase-applet-config.json`.

## اختبار القواعد محلياً

```bash
pnpm run test:rules
```

يشغّل المحاكي الرسمي (يتطلب Java) على `firestore.rules` نفسه الذي يُنشر.
